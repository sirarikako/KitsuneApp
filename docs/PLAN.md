### 1.1 必须采用的最新用餐规则

以下修改优先于早期方案：

1. **“是否计划在家吃”必填，只能选择“是／否”。** 新建表单不预选；界面尚未选择的临时状态不允许保存，不提供“未填写”选项。
2. **删除原来的“是否下厨”布尔字段，改为“用餐方式”单选分类。** 初始选项为“下厨、外卖”，可在设置中维护。
3. 计划在家吃为“是”时，用餐方式必须选择一项；为“否”时仍显示，可以不填，但最多选择一项。
4. 每种用餐方式都可以设置“显示制作分类”。默认“下厨”开启、“外卖”关闭；新增方式默认关闭，可自行开启。
5. “炒菜、预制菜”等是独立的、多选的**制作分类**，不是用餐方式。它们仍支持录入时手动新增并在下次下拉选择。
6. “是”改为“否”时保留已填写的用餐方式和制作分类。不能自动把“外卖”等同于“不在家吃”，也不能根据计划自动推断实际方式。

## 2. 产品定位、范围与默认值

### 2.1 目标

开发一个自己长期使用、可以逐步追加功能的 Android 个人工具箱，暂名 **KitsuneApp**。第一版包含：

- 用餐记录：记录每天三餐、在家吃的计划、用餐方式、制作分类、菜品与备注。
- 记账：多个钱包、独立币种、收支、分类、计算器金额输入、转账、退款、查询与月度统计。
- 数据管理：完整 JSON 备份与恢复、标准 CSV 导入导出、每次更新后的指定文件夹自动备份、GitHub 私有库备份与主动恢复。
- 个性化：柔和生活卡片风格、预设调色板、自选主色、跟随系统明暗、系统动态取色、原创卡通狐狸头像图标。

### 2.2 使用边界

- 单手机为主，本地数据库为业务数据的唯一事实来源；日常记录、查询和统计无需联网。
- GitHub 的作用是云端备份、版本历史和换机恢复，不是多设备双向实时同步。
- 不依赖自建服务器，不设置应用账号注册流程；GitHub 连接是可选配置。
- 第一版用餐与记账独立录入，不自动将用餐转换成账目。
- 第一版不做预算、信用卡账单、借贷、分期、自动汇率、折算总资产、多设备冲突自动合并、照片附件或运行时插件系统。

### 2.3 实施默认值

以下是已经提出的实现默认值，不要求用户在开发前再次选择：

- 平台：Android 8.0／API 26 及以上，首版简体中文，通过签名 APK 安装。
- 技术：Kotlin、Jetpack Compose、Material 3、Room、WorkManager。
- 外观：柔和圆角卡片，默认“跟随系统明暗＋杏橙预设”。
- 钱包：用户自行创建，币种必须明确选择，初始余额默认 0；不预设所有钱包使用人民币或其他同一币种。
- 分类：收入、支出各提供一个“未分类”兜底项；其他记账分类可自行增加。制作分类初始提供“炒菜、预制菜”。
- 本地自动备份：用户授权后启用，保留最近 30 个成功版本。
- 云端备份：用户配置并连接成功后启用，默认允许任意联网方式，可改为仅 Wi-Fi。
- 完整备份采用可阅读、未加密的 JSON；凭证不进入备份。
- 第一次录入用餐不预选在家吃或用餐方式；记账默认支出、今天、最近使用的钱包。

## 3. 信息架构与主要页面

底部四个入口固定为“首页、用餐、记账、设置”。后续新功能优先通过首页功能入口扩展，避免不断增加底部标签。

| 页面 | 内容与主要操作 |
| --- | --- |
| 首页 | 当前日期与日期切换、当天三餐卡片、快捷记账、本月按币种展示的收支摘要、备份状态入口 |
| 用餐 | 按日浏览、月历定位、历史搜索、记录详情与编辑、用餐方式和制作分类统计 |
| 记账 | 页内“流水、钱包、统计”标签；固定“记一笔”按钮；日期、钱包、类型、分类与关键词筛选 |
| 设置 | 用餐方式、制作分类、收支分类、外观与调色板、导入导出、本地备份、GitHub 配置 |

- 首页空餐卡片点击进入新增，已有卡片点击查看或编辑。
- 快捷记账直接进入金额输入流程，减少层级。
- 金额、餐次和保存按钮优先突出；收入、支出、错误与成功同时使用文字或符号表达，不只靠颜色。
- 所有主要页面支持深色模式、大字体和键盘展开；保存按钮不能被键盘遮住。
- 数据为空时提供创建或录入入口；备份未配置、等待、失败和成功都要有明确状态。

## 4. 用餐功能详细规则

### 4.1 记录字段

| 字段 | 规则 |
| --- | --- |
| 日期 | 必填，默认今天，可补录其他日期，作为日历日期保存 |
| 餐次 | 必填，早餐／午餐／晚餐 |
| 是否计划在家吃 | 必填，是／否；表单初始未选择，保存前必须选择 |
| 用餐方式 | 单选；计划在家吃为是时必填，为否时选填；没有自动默认项 |
| 制作分类 | 根据方式配置显示，多选且选填，支持搜索已有分类与输入新分类 |
| 菜品内容 | 选填，多行文本，例如“番茄炒蛋、米饭、冷冻饺子” |
| 备注 | 选填，多行文本；对应用户最初所说的“备考” |

同一日期同一餐次最多一条记录。编辑时修改日期或餐次如发生冲突，应提示已有记录，不覆盖、不生成重复项。

“是否计划在家吃”表示原先的计划，用餐方式用于记录实际方式，两者独立。例如计划在家吃为否，最后实际下厨，是合法记录。

### 4.2 用餐方式设置

- 初始建立“下厨”和“外卖”两项，使用稳定 ID 引用，不根据显示名称判断业务行为。
- 设置页面支持新增、改名、排序、停用，以及“显示制作分类”开关。
- 默认下厨开启分类开关，外卖关闭；新增项默认关闭。
- 用餐方式通过设置管理；本版不在记录表单中直接自由输入一个未经配置的方式。
- 已被引用的方式只允许停用，不硬删除；停用后不供新记录选择，已有记录可以显示并保持原选择。
- 改名后记录通过同一个 ID 关联，显示更新后的名称，不创建重复方式。

### 4.3 制作分类与状态切换

- 制作分类是所有启用该能力的方式共用的一套词表，支持多选。
- 输入新分类并保存记录时，在同一事务中创建分类和记录关联；取消表单不创建分类。
- 去除首尾空格，避免规范化后重名；支持重命名、排序、停用，已引用项不硬删除。
- 计划在家吃由是改为否，保留当前方式和分类；由否改为是且尚无方式时，要求补选后才能保存。
- 用户清空方式，或主动切换到关闭分类开关的方式时，保存后清除该条记录的制作分类；取消编辑则不改变原数据。
- 切换到另一个启用分类开关的方式时可以保留现有制作分类。
- 仅在设置里关闭某方式的分类开关，不批量清空历史记录。历史已有分类继续可查看；编辑备注等其他字段且未改变方式时，保留原分类，可显示为“历史制作分类”。
- 菜品内容、备注在所有情况下都显示，不随方式切换清空。

### 4.4 查询、复用与统计

- 按日期／餐次／用餐方式／制作分类筛选，按菜品或备注关键词搜索。
- “复制上一餐内容”复制上一条较早记录的制作分类、菜品和备注，保留当前日期、餐次及在家吃选择。当前方式未启用分类时不复制制作分类。
- 月度统计包括已记录餐数、计划在家吃的是／否餐数、各用餐方式餐数、各制作分类次数。
- 用餐方式未填的合法记录单列为“未填写”，不能推断为外卖或其他方式。
- 制作分类逐项计数，分类次数之和可以大于餐数；历史仍保留的分类也按记录计数。
- 不再以旧的“是否下厨”布尔值统计。可以在方式分布中查看下厨次数，但不依赖方式名称硬编码。

## 5. 记账功能详细规则

### 5.1 钱包

- 每个钱包保存名称、ISO 币种及其 currencyScale、初始余额、排序和归档状态。同一数据集内“规范化名称＋币种”唯一，使 CSV 映射无歧义；不同币种允许同名钱包。
- 币种精度跟随所选货币，例如 JPY 为整数，CNY 为两位小数；不使用固定两位小数处理所有币种。
- 初始余额允许为正、零或负，钱包当前余额允许为负。
- 余额由初始余额和全部相关流水计算，不另维护容易与流水不一致的可编辑余额副本。
- 修改初始余额会重新计算余额，不计为收入或支出。
- 钱包产生流水后不能改变币种或精度；已有流水的钱包只能归档，历史数据和统计保留。
- 初次没有钱包时，引导先创建钱包；归档钱包不作为新账目默认选择，历史账目仍可查看。

### 5.2 收支与分类

- 每条收入／支出包含日期、钱包、正数金额、对应类型的一个分类和可选备注。
- 收入、支出分类分别管理，采用一级分类，支持创建、改名、排序、停用和录入时新增。
- 各自保留一个“未分类”兜底项，不允许删除或停用该兜底项；业务按稳定 ID 判断，不按文字名称判断。
- 已被引用的普通分类只停用、不硬删；重命名通过引用反映到历史记录。
- 新建默认支出、今天、最近使用的未归档钱包；记住的分类必须匹配当前收支类型。
- 首版编辑不把已有流水跨类型转换；需要转换时删除原记录后新增，受退款关联等约束保护。

### 5.3 金额计算器

- 支持数字、小数点、加减乘除、退格、清空、等号，不做科学计算器或任意脚本求值。
- 采用通常的乘除优先于加减规则，例如 `12+8×2` 为 `28`。
- 使用十进制精确计算，最终按钱包货币精度采用 HALF_UP 四舍五入，并在保存前展示结果。
- 以币种最小单位的 64 位整数保存金额，所有转换和加总检查溢出；不使用 Float／Double 作为金额存储或计算依据。
- 除零、非法表达式、溢出及最终非正数不能保存，保留输入并显示可理解的错误。
- 录入页上方选择类型、钱包、分类、日期，中间显示表达式与结果，下方是计算器，备注可展开。

### 5.4 转账

- 一次转账选择两个不同钱包，作为一条整体业务记录提交、编辑和删除，数据库操作必须原子化。
- 同币种：转出和到账金额相同，填写一侧即可同步另一侧。
- 跨币种：分别填写转出金额和到账金额，例如 CNY 100 → JPY 2,000，不要求维护汇率。
- 转账不计入收入或支出，分别影响两侧钱包余额。
- 手续费单独记录为支出，不隐藏在跨币种转账金额或统计中。

### 5.5 退款

- 从原支出发起，支持部分或全部退款；退款为独立记录并引用原支出。
- 退款进入与原支出相同币种的钱包，默认原钱包；钱包不同但币种相同也允许。
- 累计退款不得大于原支出金额，退款金额必须为正。
- 按退款发生日期抵减原支出分类的支出，不作为普通收入；当月净支出可以因此为负。
- 退款分类由原支出决定，不独立编辑。修改原支出分类后，统计按其当前关联分类保持一致。
- 修改原支出金额不得小于已退款总额；存在退款时不得将原支出改成不兼容币种；删除原支出前必须先删除关联退款。
- 修改或删除退款后，余额、剩余可退金额和统计同步更新。

### 5.6 查询与统计

- 流水支持日期范围、钱包、类型、分类和备注关键词筛选，默认展示当月并按日期倒序。
- 展示月度收入、净支出、分类排行、钱包余额；归档钱包的历史流水仍参与相应期间统计。
- 所有统计按币种分别展示，不把不同货币直接相加，也不展示没有汇率依据的统一总资产。
- 转账不计收支；退款抵减支出；初始余额不计收入。余额公式包含所有流入流出，不能只用当月流水推算。

## 6. 外观、调色板与系统主题

### 6.1 独立的两个设置维度

入口：“设置 → 外观与调色板”。

| 设置 | 选项 | 默认 |
| --- | --- | --- |
| 明暗模式 | 跟随系统／浅色／深色 | 跟随系统 |
| 配色来源 | 预设调色板／自选主色／系统动态取色 | 预设调色板 |

明暗与配色来源可以自由组合，例如“茶绿＋跟随系统明暗”或“系统动态取色＋固定深色”。

### 6.2 预设与自选颜色

| 预设 | 种子色 |
| --- | --- |
| 杏橙（默认） | `#C47A4A` |
| 茶绿 | `#5F7F64` |
| 雾蓝 | `#587C9B` |
| 薰衣草 | `#8A729F` |
| 豆沙粉 | `#A76F82` |

- 自选主色同时支持可视化取色器和六位 HEX 输入，接受带或不带 `#`，保存为规范化不透明 RGB 颜色，不提供透明度。
- 第一次自选以杏橙初始化。无效 HEX 不允许应用，不丢失上次有效颜色。
- 预设与自选主色都通过 Material Color Utilities 的 Tonal Spot 色彩方案生成完整浅色与深色 ColorScheme，不把原色直接作为全部背景或正文颜色。
- 为主色、辅助色、卡片、背景、文字、边框、选中态提供统一主题颜色；业务页面不得散落硬编码品牌色。
- 收入、支出、成功、错误采用独立语义色，并适配明暗模式；配色不能让金额类型只能靠颜色判断。

### 6.3 系统跟随与兼容

- 明暗“跟随系统”响应系统明暗变化；固定浅色／深色时不跟随变化。
- 系统动态取色使用系统提供的 Material 配色，不自行读取或上传用户壁纸。
- 动态取色在 Android 12／API 31 及以上可选；较早版本禁用该选项并说明版本要求。
- 恢复备份到不支持动态取色的设备时保留用户偏好，实际使用保存的预设，缺省为杏橙；明暗设置仍有效。
- 切换来源时保留上一次预设、自选主色，以便切回。
- 系统栏与应用内容统一适配；应用回到前台时也能刷新系统配色。

### 6.4 预览、保存和备份

- 调色页展示用餐卡片、收入／支出行、标签、按钮和背景预览，可分别预览浅色、深色，不改变全局明暗设置。
- 拖动取色器、输入颜色和选择预设只修改预览草稿；点击“应用”后全应用更新，无需重启。
- 取消不改变已应用设置；“恢复默认”恢复跟随系统明暗、杏橙预设，仍通过应用按钮提交。
- 只在应用实际不同的设置时持久化并触发一次备份；拖动、无变化提交、系统明暗或壁纸变化不产生备份。
- 主题设置纳入 JSON 完整备份，换机后可以恢复。
- 普通正文及重要文字与背景的对比度验收目标至少为 4.5:1；极浅、极深和高饱和种子色都应保持可读性。

## 7. APP 图标

用户已授权由实现者自行完成图标设计，不再要求用户选择风格。当前尚未生成图像。

### 7.1 视觉规格

- 原创、正面卡通狐狸头像，暖橙色毛发、奶白色脸颊、圆润脸部、尖耳朵、轻微微笑。
- 扁平插画风，轮廓清楚，缩小后仍容易辨认。
- 彩色图标使用奶油色背景，不加文字、水印或多余装饰，与柔和生活卡片风格协调。
- 不将狐狸永久画入已裁切的圆角方形中；背景与前景分离，由 Android 启动器决定最终外形。

### 7.2 资产与接入

- 实施时按可用 imagegen 技能使用内置图像生成工具制作原创彩色前景，前景透明；背景作为独立层。
- 保存高分辨率源图和项目使用的最终资源到仓库，不能只引用会话或工具默认输出目录。
- 配置 Android Adaptive Icon 的前景、背景和独立单色层；单色层要保留狐狸的识别特征，不能简单变成一个没有五官的实心轮廓。
- 按 108×108 dp 图层设计，主体关键内容在中央 66×66 dp 安全区域，适配圆形、圆角方形等遮罩，不预画外部投影或遮罩。
- 支持 Android 13 及以上兼容启动器的主题图标。彩色版保持品牌配色，单色版由系统主题着色；应用内调色板不直接改写桌面图标资源。
- 接入启动器图标资源与 manifest，检查不同形状、主题模式和实际小尺寸效果。
- 工程内保留最终生成提示词及资产说明，便于后续继续修改同一形象。

## 8. 技术架构与核心数据接口

### 8.1 结构

- 用 Kotlin 与 Compose 构建原生界面，统一使用 Material 3 设计系统。
- UI → ViewModel → Repository → Room；界面观察本地状态，备份服务不能成为读取业务数据的前置依赖。
- 按 `feature/meals`、`feature/ledger`、`feature/settings` 分包，核心能力放入数据库、主题／组件、备份、文件访问等共享包。
- 第一版采用按功能分包的单体应用，不为两个业务模块引入动态插件或独立后端。
- 新功能接入应用导航、首页卡片、自己的实体与业务逻辑，以及统一备份的导出／校验／恢复处理。
- 选择实施时相互兼容的稳定工具链和依赖，集中锁定版本；不得使用浮动依赖版本。实际 JDK、SDK 和构建命令验证后记录在 README 与 AGENTS.md。

### 8.2 实体与约束

| 对象 | 最低必需信息 |
| --- | --- |
| MealRecord | UUID、date、mealSlot、plannedAtHome（不可空布尔值）、mealMethodId（可空引用）、dishes、note、createdAt、updatedAt；日期与餐次唯一 |
| MealMethod | UUID、name、normalizedName、sortOrder、archived、showPreparationCategories；初始下厨／外卖 |
| Category | UUID、scope（PREPARATION／INCOME／EXPENSE）、name、normalizedName、sortOrder、archived、isDefault；同域规范化名称唯一，收支各有一个兜底项 |
| MealPreparationCategory | mealId、categoryId，唯一联合关联，多对多 |
| Wallet | UUID、name、normalizedName、currencyCode、currencyScale、openingBalanceMinor、sortOrder、archived、时间戳 |
| FinancialEntry | UUID、date、type（INCOME／EXPENSE／TRANSFER／REFUND）、walletId、amountMinor、categoryId、toWalletId、toAmountMinor、originalExpenseId、note、时间戳 |
| ThemePreferences | themeMode（SYSTEM／LIGHT／DARK）、colorSource（PRESET／CUSTOM／SYSTEM）、presetId、customSeedColor |
| ImportReceipt | kind（MEALS／LEDGER）、源文件 sha256、importedAt；随 JSON 迁移，防止同一无 ID CSV 重复导入 |
| DataState／BackupOutbox | 数据集标识、本地修订号、快照标识与不可变内容、各目标完成状态、失败信息；不能进入业务备份自身 |

- FinancialEntry 的 walletId 对收入／支出／退款表示对应钱包，对转账表示转出钱包；toWalletId 和 toAmountMinor 只用于转账。
- 转账使用两侧钱包的货币精度；退款通过 originalExpenseId 引用原支出，分类从原支出取得。
- UUID 是业务数据身份，显示名称可改，所有关联用 ID，不用中文字符串作为外键或条件。
- 数据库中的金额为 Long；JSON 中金额与 revision 以十进制字符串传输，避免中间工具损失整数精度。具体字段与示例以 DATA_FORMAT.md 为准。
- 规范化分类名至少包含去除首尾空格和大小写无关比较；保留用户显示写法。各分类域不互相混用。
- 日历日期保存为 `YYYY-MM-DD`，不把当地日期先转换成 UTC 再按 UTC 分组；createdAt／updatedAt 使用 UTC。
- 只在表单草稿允许 plannedAtHome 尚未选择。持久化、CSV 导入、JSON 恢复都必须满足其非空约束。
- plannedAtHome 为 true 时 mealMethodId 不可空；false 时可以为空。mealMethodId 为空时制作分类必须为空。
- 方式当前关闭分类开关不意味着历史分类非法，不能在数据库迁移或恢复时据此清空历史关联。
- 数据库 schema 与备份 formatVersion 分别版本化；升级必须显式迁移，不能用破坏性重建丢弃用户数据。

### 8.3 事务与统一变更入口

- 记录保存、关联分类创建、转账、退款、批量导入都走业务事务；成功后才向 UI 返回保存成功。
- 所有可备份数据变更经统一入口增加修订号并安排备份，不能仅在某个页面点击保存时附加备份逻辑。
- 创建分类并保存记录算一次业务提交；CSV 批量导入算一次提交；主题应用一次算一次提交。
- 备份任务、进度、重试、系统主题变化等内部状态不能触发递归备份。
- 删除普通记录生成新的完整快照；单设备完整快照方案不要求为将来的多端合并提前引入 tombstone 系统。

## 9. 完整 JSON 备份、本地自动备份与 GitHub

### 9.1 备份格式与边界

完整备份是可阅读的 UTF-8 JSON，不是直接复制运行中的 SQLite 文件。信封至少包含：

- 固定格式标识、formatVersion，及 backupKind（AUTO／MANUAL／PRE_RESTORE）。
- datasetId、snapshotId、revision、exportedAt。
- 按模块组织的用餐、用餐方式、制作分类、收支分类、钱包、流水、可迁移设置与成功 CSV 导入凭据。
- 稳定 ID、归档状态、排序、方式分类开关和主题偏好都必须保存，以支持真正完整恢复。

不包含 GitHub Token、Keystore 密钥、文件夹授权 URI、安装设备身份、工作队列、重试状态和远端同步游标。备份目标及其授权作为本机连接配置，不随业务 JSON 覆盖；换机后重新配置目录和 GitHub 连接。

- 稳定排序输出实体与字段，便于 GitHub 比较历史。
- 编写格式迁移器，支持已经发布的旧版本；无法识别的较新版本必须拒绝恢复，不可忽略未知模块后静默丢数据。
- 不导出密码、日志中不打印 Token，凭证也须排除在 Android 系统备份／迁移规则之外。

### 9.2 每次更新的可靠性

- 本地目标启用后，每次成功的业务提交都要有对应修订的不可变快照内容。不能只存一个“稍后导出”的空任务，然后在每次执行时全部读取最新数据冒充历史版本。
- 将该修订的数据快照和待处理标记与业务修改在同一事务中提交，或采用保证同等一致性的实现；不允许提交成功后进程退出导致永久漏备份。
- 本地目录未配置时，仍保存业务数据与修订号，明确显示未启用备份；不无限积累尚不存在目标的历史导出任务。
- 首次配置目标后立即生成当前快照；不声称可以补回配置前所有未保存的历史修订。
- 本地队列串行处理每次修订；云端可以合并尚未上传的连续修订，最终上传最新完整快照。
- 新修订产生于上传期间时，上传完成不能把更高修订错误标记为已备份；继续调度下一次任务。

### 9.3 本地目录

- 通过 Storage Access Framework 的系统目录选择器授权目录并持久化授权，示例位置为 `Documents/KitsuneBackup`；不申请全盘文件访问权限。
- 每个修订写入独立 JSON 文件，文件名包含可读时间和唯一快照标识，避免同秒覆盖。
- 先写待完成文件，关闭流后校验读回内容与预期一致，再将其标记／命名为可用备份。不能假定所有文档提供方都支持原子 rename。
- 写入中断或失败不破坏旧快照；未完成文件不能出现在可恢复版本列表中。
- 新备份成功后，按快照元数据保留当前数据集最近 30 个成功 AUTO 版本；仅清理经格式与数据集标识确认属于本应用的自动快照，不清理 MANUAL／PRE_RESTORE 或目录中的其他文件。
- 目录失效、授权撤销、文件被移动、空间不足等情况保留待处理任务，显示错误与重新授权／重试入口。
- 提供“立即备份”、本地版本列表与选择恢复。打开应用时核对数据库待处理状态并补调度任务。

### 9.4 GitHub 私有库

- 用户提供目标私有仓库、分支和细粒度 Token，授权限定为该仓库的 Contents 读写权限；连接测试检查仓库和分支是否可用、是否为私有仓库。
- 数据仓库独立配置，不默认把个人生活数据提交到应用源码仓库。
- 通过 Contents API 更新固定文件 `backups/latest.json`，每次成功上传形成提交，版本历史由 GitHub 保存。
- Token 使用 Android Keystore 保护的密钥加密后保存在本机，不写入源码、导出文件或日志。
- WorkManager 根据联网条件调度、串行上传、失败退避重试；本地保存不等待网络成功。
- 短时间连续修改可以合并成最新快照上传；本地 30 版本策略与 GitHub 提交历史互不等同，云端不承诺每一次保存都单独产生提交。
- 默认任意网络，可设仅 Wi-Fi；“立即备份”用于立即发起当前可执行任务，不保证绕过 Android 系统限制。
- 首次绑定发现目标文件已有数据时，不自动覆盖，展示云端快照摘要并提供恢复云端或明确以本机替换的操作。
- 更新采用已知文件 SHA 作为并发校验。发现外部变更或冲突时暂停覆盖，不能简单读取新 SHA 后无提示重试覆盖。
- 响应丢失等重试场景先核对远端 snapshotId／内容，已上传相同快照应视为成功，避免重复提交。
- 提供云端版本历史列表、选择版本、查看时间与记录摘要并主动恢复；不自动拉取后覆盖本机。

### 9.5 状态展示

区分并分别显示：

1. 本地记录已保存。
2. 文件夹备份未配置／待处理／执行中／成功／失败，以及最新成功时间。
3. GitHub 未配置／待联网／待处理／执行中／成功／失败／远端冲突，以及最新成功时间。

后台任务可能受到系统调度、休眠或强制停止的影响，不承诺精确到秒的自动上传；任何未完成任务都不能显示为“已备份”。数据库自身保存失败时显示保存失败，不能用备份重试掩盖业务写入失败。

### 9.6 完整恢复流程

1. 将文件或所选 GitHub 版本下载／读取到暂存区，解析、迁移并校验，尚不修改业务数据。
2. 校验格式版本、字段类型、唯一性、ID 引用、金额精度、用餐必填条件、转账和退款约束；允许合法的历史归档引用。
3. 展示来源、时间、各类记录数量，并明确完整恢复将替换当前业务数据，不进行合并。
4. 暂停业务写入和云端上传，成功保存当前数据的恢复前快照；若备份无法成功，停止恢复并保留当前状态。恢复前快照作为显式导出保留，不立即受自动 30 版本清理影响。
5. 在数据库事务内整体替换业务数据和可迁移设置；任何失败都回滚。首次安装的默认分类不能在恢复后重复播种。
6. 保留本机有效连接配置，取消旧待上传内容；对恢复后的内容建立新的本地修订和快照，再重新调度备份。
7. 用快照 UUID 和远端 SHA 判断身份及冲突，不能把不同设备的 revision 大小当作同步依据；恢复旧版本后仍产生新修订，不能让旧工作覆盖恢复结果。

## 10. CSV 导入导出

CSV 用于表格查看、批量录入和记录迁移；完整钱包、分类设置、主题和全部关系迁移优先使用 JSON。

### 10.1 标准模板

- 提供 UTF-8 编码的用餐、记账模板和导出文件；导入接受 UTF-8 BOM，正确处理引号、逗号和多行字段，不能按字符串逗号简单切分。
- 使用固定英文列名，并在模板说明中提供中文解释、枚举值和示例。导出保留稳定记录 ID。
- 用餐表列：`id,date,meal_slot,planned_at_home,meal_method,preparation_categories,dishes,note`。
- 记账表列：`id,date,type,wallet,currency,amount,category,to_wallet,to_currency,to_amount,original_expense_id,note`。
- 日期格式为 `YYYY-MM-DD`；meal_slot 为 `BREAKFAST/LUNCH/DINNER`；planned_at_home 为 `true/false`，不能为空。
- meal_method 使用方式名称；preparation_categories 是分类名称的 JSON 字符串数组，嵌入 CSV 时遵守 CSV 引号转义规则，空数组表示无分类。
- 财务 type 为 `INCOME/EXPENSE/TRANSFER/REFUND`；金额为十进制文本，无千分位和货币符号，不能使用二进制浮点读写金额。
- TRANSFER 填写两侧钱包、币种和金额；非转账对应列留空。REFUND 填写 original_expense_id，分类由原支出确定。
- 金额精度超过币种支持范围时报告错误，不在导入时默默四舍五入。

### 10.2 预览与提交

- 先完成解析、名称映射和全量校验，再展示新增、重复和错误记录及具体行号。
- 钱包映射到已有钱包并校验币种；缺少钱包时先创建再导入，不通过 CSV 隐式猜测初始余额。
- 未知用餐方式需在预览中映射到已有方式，或先到设置中创建；不能猜测其分类开关。
- 新制作分类、收入分类和支出分类按各自域随导入创建；分类同名匹配现有 ID。
- 相同 ID 且业务内容相同的记录跳过；相同 ID 内容不同，或不同 ID 占用同一日期餐次时，报告冲突，不覆盖现有数据。
- 无 ID 的外部记录生成 UUID；记录成功导入文件的摘要，阻止同一文件反复导入造成重复。具有不同 ID 的合法同金额账目不能仅凭金额或备注去重。
- 退款可以引用已有支出或同批导入的支出，整体校验所有引用和累计退款额；转账作为一个整体导入。
- 若任何行有错误，要求修正后再整批提交；重复项可跳过，有效新增项在同一事务中提交并触发一次备份。
- 新导入方式为空且计划在家吃为是的用餐记录必须报错；历史制作分类的保留规则与 JSON 恢复一致，不能因方式目前关闭开关而静默丢弃分类。

## 13. 验收与测试计划

### 13.1 用餐

- 新记录未选择在家吃不能保存；选是但未选方式不能保存；选否且方式为空可保存。
- 选否时仍可选择下厨／外卖或自定义方式；是改否保留内容。
- 下厨显示多选制作分类，外卖默认不显示；新增方式开关按设置生效，改名不影响引用。
- 新分类保存后可再次下拉选择，取消不创建；同日同餐冲突不能覆盖。
- 关闭全局开关后历史分类仍可查看，修改备注不丢失历史分类；主动切换到不支持分类的方式后按规则清除。
- 月度方式分布和分类计数正确，未填方式独立统计，中文与多行文本完整保留。

### 13.2 记账

- 计算器验证运算优先级、十进制精度、除零、非法表达式、四舍五入、非正数和溢出。
- 覆盖 JPY 整数精度、两位及其他支持币种精度；货币间不混合加总。
- 同币种转账、跨币种双金额、整体编辑删除正确影响两侧余额，不计收支。
- 多次部分退款、超额退款拦截、退款删除、原支出修改约束及跨月净支出统计正确。
- 钱包初始余额、负余额、归档和已有流水后的币种限制正确。

### 13.3 外观与图标

- 三种明暗模式与三种配色来源组合正确；旧系统动态取色选项与恢复回退正确。
- 自选 HEX 校验、取色预览、应用、取消、恢复默认、重启与 JSON 恢复正确。
- 拖动不备份，系统变色不备份，一次实际应用只生成一次修订。
- 检查所有页面、弹窗、表单、图表、计算器、系统栏、大字体和键盘布局；验证关键文字对比度。
- 狐狸图标在圆形／圆角方形遮罩及小尺寸下不裁掉耳朵或五官；彩色和单色主题图标都可辨认。

### 13.4 备份、导入与恢复

- 连续保存不同内容，每次本地快照对应正确修订，不能全部变成同一个最新数据。
- 第 31 份成功后仅清理最旧的本应用同数据集快照，其他文件不变；失败时旧快照保留。
- 覆盖断网、目录失效、授权撤销、外部空间不足、进程退出和重启补任务；状态不得误报成功。
- 覆盖 Token 失效、远端文件变化、首次已有数据、上传响应丢失、上传期间又有修改；不静默覆盖，不漏最新修订。
- 在全新安装中恢复完整 JSON，用餐、方式配置、分类、钱包余额、退款／转账关系、归档状态和主题一致。
- 损坏或较新格式、无效引用、无效金额、日期餐次冲突及失败恢复都不能破坏现有数据。
- CSV 覆盖中文、引号、逗号、多行文本、制作分类数组、重复 ID、重复文件、同批退款引用、精度错误和整批回滚。
- 凭证不出现在导出文件、仓库或日志中；备份任务变化不会递归触发新备份。

### 13.5 测试实施与交付证据

- 对计算器、金额、余额、转账、退款、字段条件、CSV 和备份格式编写有实际约束意义的单元测试。
- 对 Room 关系、事务、唯一约束、恢复与迁移执行数据库／集成测试。
- 对关键表单、主题和恢复流程进行 Compose UI 测试或可复现的设备验证；文件授权、后台调度与启动器图标需模拟器／真机检查。
- 在已配置的环境运行适当的构建、lint 与测试，记录实际命令、结果和未验证的外部集成，不以截图或代码存在替代功能验证。
