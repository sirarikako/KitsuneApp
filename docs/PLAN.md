### 1.1 必须采用的最新用餐规则

以下修改优先于早期方案：

1. **“是否计划在家吃”必填，只能选择“是／否”。** 新建表单不预选；界面尚未选择的临时状态不允许保存，不提供“未填写”选项。
2. **删除原来的“是否下厨”布尔字段，改为“用餐方式”单选分类。** 初始选项为“下厨、外卖”，可在设置中维护。
3. 计划在家吃为“是”时，用餐方式必须选择一项；为“否”时仍显示，可以不填，但最多选择一项。
4. 每种用餐方式都可以设置“显示制作分类”。默认“下厨”开启、“外卖”关闭；新增方式默认关闭，可自行开启。
5. “炒菜、预制菜”等是独立的、多选的**制作分类**，不是用餐方式。它们仍支持录入时手动新增并在下次下拉选择。
6. “是”改为“否”时保留已填写的用餐方式和制作分类。不能自动把“外卖”等同于“不在家吃”，也不能根据计划自动推断实际方式。

## 2. 产品定位、范围与默认值

### 2.1 目标

开发一个自己长期使用、可以逐步追加功能的 Android 个人工具箱，暂名 **KitsuneApp**。第一版包含：

- 用餐记录：记录每天三餐、在家吃的计划、用餐方式、制作分类、菜品与备注。
- 记账：多个钱包、独立币种、收支、分类、计算器金额输入、转账、退款、查询与月度统计。
- 数据管理：完整 JSON 备份与恢复、标准 CSV 导入导出、指定文件夹与 GitHub 私有库的最新完整数据自动备份。
- 个性化：柔和生活卡片风格、预设调色板、自选主色、跟随系统明暗、系统动态取色、原创卡通狐狸头像图标。

### 2.2 使用边界

- 单手机为主，本地数据库为业务数据的唯一事实来源；日常记录、查询和统计无需联网。
- GitHub 用于保存最新完整云端备份。换机时由用户主动恢复。
- 不依赖自建服务器，不设置应用账号注册流程；GitHub 连接是可选配置。
- 第一版用餐与记账独立录入，不自动将用餐转换成账目。
- 第一版不做预算、信用卡账单、借贷、分期、自动汇率、折算总资产、多设备冲突自动合并、照片附件或运行时插件系统。

### 2.3 实施默认值

以下是已经提出的实现默认值，不要求用户在开发前再次选择：

- 平台：Android 8.0／API 26 及以上，首版简体中文，通过签名 APK 安装。
- 技术：Kotlin、Jetpack Compose、Material 3、Room、WorkManager。
- 外观：柔和圆角卡片，默认“跟随系统明暗＋杏橙预设”。
- 钱包：用户自行创建，币种必须明确选择，初始余额默认 0；不预设所有钱包使用人民币或其他同一币种。
- 分类：收入、支出各提供一个“未分类”兜底项；其他记账分类可自行增加。制作分类初始提供“炒菜、预制菜”。
- 本地自动备份：用户授权后启用，每个数据集在该目录保留一份最新成功的完整自动备份。
- 云端备份：用户配置并连接成功后启用，默认允许任意联网方式，可改为仅 Wi-Fi。GitHub 自动上传合并连续变更，后台最小上传间隔为 30 分钟，详见第 9.4 节。
- 完整备份采用可阅读、未加密的 JSON；凭证不进入备份。
- 第一次录入用餐不预选在家吃或用餐方式；记账默认支出、今天、最近使用的钱包。

## 3. 信息架构与主要页面

底部四个入口固定为“首页、用餐、记账、设置”。后续新功能优先通过首页功能入口扩展，避免不断增加底部标签。

| 页面 | 内容与主要操作 |
| --- | --- |
| 首页 | APP 图标与“日常记录”标题、当前日期、今日三餐记录进度、按时段推荐餐次的快捷记录、快捷记账、本月按币种展示的收支摘要 |
| 用餐 | 按日浏览、月历定位、历史搜索、记录详情与编辑、用餐方式和制作分类统计 |
| 记账 | 页内“流水、钱包、统计”标签；固定“记一笔”按钮；日期、钱包、类型、分类与关键词筛选 |
| 设置 | 用餐方式、制作分类、收支分类、外观与调色板、导入导出、本地备份、GitHub 配置 |

- 首页不重复用餐页的日期浏览和三餐详情；显示当天记录进度，并按设备本地时间推荐餐次：00:00–10:59 早餐、11:00–16:59 午餐、17:00–23:59 晚餐。对应餐次未记录时显示“记录早餐／午餐／晚餐”，已有记录时显示“编辑早餐／午餐／晚餐”，不跳到另一餐，也不自动创建记录。其他餐次和补录通过用餐页进入；应用回到前台或跨时段时刷新推荐。
- 首页使用 APP 图标与“日常记录”文字作为标题，不显示问候标语、备份是否启用或备份状态入口。备份状态与操作集中在设置页；设置统一由底部导航进入，不常驻右上角。
- 快捷记账直接进入金额输入流程，减少层级。
- 金额、餐次和保存按钮优先突出；收入、支出、错误与成功同时使用文字或符号表达，不只靠颜色。
- 所有主要页面支持深色模式、大字体和键盘展开；保存按钮不能被键盘遮住。
- 数据为空时提供创建或录入入口；备份未配置、等待、失败和成功都要有明确状态。

### 3.1 用餐与账本的共用界面

| 组件 | 统一规则 |
| --- | --- |
| 导航与筛选 | 共用页标题、页内下划线标签和带边框的筛选控件。两边的月度视图使用相同的月份选择器。用餐继续支持按日和组合筛选，账本流水与统计继续共享日期及钱包范围。 |
| 记录列表 | 三餐、用餐筛选结果和账本流水使用同一记录行组件，共用图标尺寸、主次文字、标签、间距和详情箭头。两套方案均使用带细描边的圆角记录卡片，仅按各自主题调整圆角和颜色。待记录餐次使用加号，用餐历史展示菜品与餐次，账本流水右对齐带正负号及币种的金额。 |
| 录入与详情 | 子页左侧统一放返回按钮，录入共用字段标签、输入框、选项和保存按钮样式。校验提示放在操作区，删除使用相同的危险操作样式与确认弹窗。金额和计算器保留独立输入区。 |
| 统计 | 共用分组标题、两列摘要和明细面板。用餐分布按餐数显示比例条，账本按币种显示收支及分类金额。 |

**容器与控件统一规范：** 首页收支、今日用餐、用餐／账本记录行、统计摘要与明细、账目详情、设置分组和外观示例均使用主题卡片底色及 1px 细描边，不用整块强调色替代边框，也不因切换视觉方案改为仅底部分隔线。筛选、输入、普通选择和计算器数字键保持同一描边体系。纯色强调只用于主操作按钮、明确的当前选中态、危险确认、品牌／状态图标及图表／调色板等具有语义的元素；未选中控件和一般信息卡片不铺大面积强调色。浅色、深色与系统动态颜色都使用相同的语义色角色和交互规则。

**共用设计规格（网页基准，Android 对应 dp／sp 并支持字体放大）：** 间距使用 4／8／12／16／24；普通卡片内边距 16、紧凑记录 12；卡片圆角杏橙 17、清爽 13，控件 12，弹窗 24。普通输入、主要与次要按钮最小高度 46，独立图标按钮 44×44，标准图标 18；正文 14、辅助文字 12、标签 11、页面标题 26、分组标题 15。尺寸为基准而非固定高度，长文字允许换行增高。日期、普通选项和制作分类筛选的选中状态使用主题浅色底与主题色描边，保留多选勾选符号；页内标签下划线、底部导航指示和待记录虚线保留各自语义。金额输入保留大字及右对齐，但使用同一描边输入样式。设置下拉控件、账目详情分组与弹窗使用共用样式；计算器与钱包保持底部弹层，删除保持居中确认框。

两种方案都把背景、卡片、正文、辅助文字、选中和危险态映射到同一套主题角色。预览中记录行以约 70 CSS px 为基准，长内容及字体放大时允许增高。紧凑历史行可截断摘要，进详情后可读完整内容；金额和币种须可辨认。

## 4. 用餐功能详细规则

### 4.1 记录字段

| 字段 | 规则 |
| --- | --- |
| 日期 | 必填，默认今天，可补录其他日期，作为日历日期保存 |
| 餐次 | 必填，早餐／午餐／晚餐 |
| 是否计划在家吃 | 必填，是／否；表单初始未选择，保存前必须选择 |
| 用餐方式 | 单选；计划在家吃为是时必填，为否时选填；没有自动默认项 |
| 制作分类 | 根据方式配置显示，多选且选填，支持搜索已有分类与输入新分类 |
| 菜品内容 | 选填，多行文本，例如“番茄炒蛋、米饭、冷冻饺子” |
| 备注 | 选填，多行文本；对应用户最初所说的“备考” |

同一日期同一餐次最多一条记录。编辑时修改日期或餐次如发生冲突，应提示已有记录，不覆盖、不生成重复项。

已有用餐记录的编辑页底部提供明确的“删除这条用餐记录”按钮；新增页不显示删除。点击后先展示待删除记录的原日期、餐次和菜品摘要，确认后才删除，取消保留当前编辑草稿。删除后更新首页进度、月度统计及全部记录统计；不能因编辑中的日期／餐次草稿变化而删除另一条记录。

“是否计划在家吃”表示原先的计划，用餐方式用于记录实际方式，两者独立。例如计划在家吃为否，最后实际下厨，是合法记录。

### 4.2 用餐方式设置

- 初始建立“下厨”和“外卖”两项，使用稳定 ID 引用，不根据显示名称判断业务行为。
- 设置页面支持新增、改名、排序、停用，以及“显示制作分类”开关。
- 默认下厨开启分类开关，外卖关闭；新增项默认关闭。
- 用餐方式通过设置管理；本版不在记录表单中直接自由输入一个未经配置的方式。
- 已被引用的方式只允许停用，不硬删除；停用后不供新记录选择，已有记录可以显示并保持原选择。
- 改名后记录通过同一个 ID 关联，显示更新后的名称，不创建重复方式。

### 4.3 制作分类与状态切换

- 制作分类是所有启用该能力的方式共用的一套词表，支持多选。
- 输入新分类并保存记录时，在同一事务中创建分类和记录关联；取消表单不创建分类。
- 去除首尾空格，避免规范化后重名；支持重命名、排序、停用，已引用项不硬删除。
- 计划在家吃由是改为否，保留当前方式和分类；由否改为是且尚无方式时，要求补选后才能保存。
- 用户清空方式，或主动切换到关闭分类开关的方式时，保存后清除该条记录的制作分类；取消编辑则不改变原数据。
- 切换到另一个启用分类开关的方式时可以保留现有制作分类。
- 仅在设置里关闭某方式的分类开关，不批量清空历史记录。历史已有分类继续可查看；编辑备注等其他字段且未改变方式时，保留原分类，可显示为“历史制作分类”。
- 菜品内容、备注在所有情况下都显示，不随方式切换清空。

### 4.4 查询、复用与统计

- “用餐 → 记录”提供明确的“筛选”入口，支持起止日期（含边界，可留空）、餐次、是否计划在家吃、用餐方式（含“未填写”）、制作分类和菜品／备注关键词。各维度组合为同时满足；制作分类可多选，匹配任一所选分类；日期开始晚于结束时提示错误，不应用。
- 应用后切换为跨日期的匹配记录列表，显示结果数、已应用条件、原日期与餐次、方式、制作分类、菜品和备注；支持清空条件和返回按日浏览。点开结果仍能编辑、删除原记录，保存／删除后重新计算匹配结果并保留筛选条件。筛选页“重置条件”只重置草稿，应用后生效，返回不改变已应用条件。记录筛选不改变统计页的月份范围及全部记录统计。
- 匹配记录使用第 3.1 节的紧凑记录行，依次显示菜品、日期与餐次及方式、计划／制作分类／备注摘要。过长的菜品和摘要省略显示，点开可查看完整内容；保持正文字号及原始记录内容。
- “复制上一餐内容”复制上一条较早记录的制作分类、菜品和备注，保留当前日期、餐次及在家吃选择。当前方式未启用分类时不复制制作分类。
- 月度统计包括已记录餐数、计划在家吃的是／否餐数、各用餐方式餐数、各制作分类次数。
- 用餐统计页顶部提供明确的月份选择器，可直接选择年月或切换上／下个月；月度概览、用餐方式和制作分类随所选月份更新，无记录月份显示空状态。
- 用餐统计页最下面另设“全部记录 · 用餐方式”，按全部历史记录展示各方式餐数及占比，不受上方月份选择影响。分母为全部已记录餐数，合法的方式未填记录单列“未填写”；历史停用方式仍参与统计。
- 统计同时展示数值与横向条形：月度及全部记录的用餐方式条形按对应已记录餐数表示占比，保留名称、餐数及百分比；月度制作分类显示次数及占当月记录餐数的比例（可多选，比例之和可超过 100%）。计划在家的是／否以有文字标注的分段条形表示；无数据时不绘制有长度的条形。
- 用餐方式未填的合法记录单列为“未填写”，不能推断为外卖或其他方式。
- 制作分类逐项计数，分类次数之和可以大于餐数；历史仍保留的分类也按记录计数。
- 不再以旧的“是否下厨”布尔值统计。可以在方式分布中查看下厨次数，但不依赖方式名称硬编码。

## 5. 记账功能详细规则

### 5.1 钱包

- 每个钱包保存名称、ISO 币种及其 currencyScale、初始余额、排序和归档状态。同一数据集内“规范化名称＋币种”唯一，使 CSV 映射无歧义；不同币种允许同名钱包。
- 币种精度跟随所选货币，例如 JPY 为整数，CNY 为两位小数；不使用固定两位小数处理所有币种。
- 初始余额允许为正、零或负，钱包当前余额允许为负。
- 余额由初始余额和全部相关流水计算。派生余额按最小货币单位用任意精度整数计算和展示，可超过单笔金额的 64 位范围。
- 修改初始余额会重新计算余额，不计为收入或支出。
- 钱包产生流水后不能改变币种或精度；已有流水的钱包只能归档，历史数据和统计保留。
- 初次没有钱包时，引导先创建钱包；归档钱包不作为新账目默认选择，历史账目仍可查看。

### 5.2 收支与分类

- 每条收入／支出包含日期、时间、钱包、正数金额、对应类型的一个分类和可选备注。收入、支出、转账和退款都必须记录业务发生时间，精确到分钟（24 小时制 HH:mm）。新建时日期和时间从打开表单时的设备本地时钟一次性带入，允许手动修改；保存时不覆盖用户选择，编辑旧记录时保留原日期和时间。
- 收入、支出分类分别管理，采用一级分类，支持创建、改名、排序、停用和录入时新增。
- 各自保留一个“未分类”兜底项，不允许删除或停用该兜底项；业务按稳定 ID 判断，不按文字名称判断。
- 已被引用的普通分类只停用、不硬删；重命名通过引用反映到历史记录。
- 新建默认支出、今天、最近使用的未归档钱包；记住的分类必须匹配当前收支类型。
- 首版编辑不把已有流水跨类型转换；需要转换时删除原记录后新增，受退款关联等约束保护。

### 5.3 金额计算器

- 支持数字、小数点、加减乘除、退格、清空、等号，不做科学计算器或任意脚本求值。
- 采用通常的乘除优先于加减规则，例如 `12+8×2` 为 `28`。
- 将有限小数解析为精确分数，保留除法产生的分数直到整条表达式计算结束。只在最终按钱包货币精度采用 HALF_UP 四舍五入，并展示待保存结果。例如两位小数的钱包中，`1÷3×100` 得到 `33.33`。
- 单笔金额及钱包初始余额以币种最小单位的有符号 64 位整数保存。退款累计、派生余额和统计加总使用任意精度整数，结果按币种精度直接格式化。
- 除零、非法表达式、舍入后超出单笔金额范围或最终非正数时保留输入并提示错误。编辑或删除后的派生余额可以超过 64 位范围，按精确金额正常显示。
- “记一笔”主表单采用紧凑的单页布局：日期时间（支持时、分）、钱包与分类（同一行）、备注、金额，最后保存；收支类型放在页标题区。金额可直接输入，旁边提供“计算器”入口，默认不常驻完整计算键盘。计算器以底部弹层打开，“使用此金额”后回填结果并关闭；取消、返回或关闭保留原金额。打开／关闭和计算不得清空日期时间、钱包、分类、备注等草稿。常规字号且键盘关闭时以一屏完成为目标；大字体或键盘展开时允许滚动，确保保存按钮可达。

### 5.4 转账

- 一次转账选择两个不同钱包，作为一条整体业务记录提交、编辑和删除，数据库操作必须原子化。
- 同币种：转出和到账金额相同，填写一侧即可同步另一侧。
- 跨币种：分别填写转出金额和到账金额，例如 CNY 100 → JPY 2,000，不要求维护汇率。
- 转账不计入收入或支出，分别影响两侧钱包余额。
- 手续费单独记录为支出，不隐藏在跨币种转账金额或统计中。

### 5.5 退款

- 从原支出发起，支持部分或全部退款；退款为独立记录并引用原支出。
- 退款进入与原支出相同币种的钱包，默认原钱包；钱包不同但币种相同也允许。
- 累计退款不得大于原支出金额，退款金额必须为正。
- 退款按自身发生日期和到账钱包计入流水，抵减该日期及钱包范围内原支出分类的净支出。当期净支出可以为负。例：同币种的 A 钱包支出 100，B 钱包到账退款 30，在两笔均落入所选日期范围时，单选 A 的净支出为 100，单选 B 为 −30，合选 A 和 B 为 70。
- 退款分类由原支出决定，不独立编辑。修改原支出分类后，统计按其当前关联分类保持一致。
- 修改原支出金额不得小于已退款总额；存在退款时不得将原支出改成不兼容币种；删除原支出前必须先删除关联退款。
- 修改或删除退款后，余额、剩余可退金额和统计同步更新。

### 5.6 查询与统计

- 流水支持日期范围、钱包、类型、分类和备注关键词筛选，默认展示当月，按业务日期、业务时间倒序；同一分钟的记录再按 createdAt 倒序、ID 升序稳定排列。流水行和详情显示业务时间。
- 流水与统计共用一个已应用的日期范围。默认使用本月，月份选择器可直接选择年月或切换上／下个月。自定义范围必须填写开始、结束日期，可跨月且包含两端；应用后替换月份范围，两个标签都显示实际起止日期。选择“返回按月”回到上次所选月份。取消或输入无效时保留已应用范围。
- 日期与钱包范围同时作用于流水、收支摘要和分类统计。钱包范围支持全部、单个或自选多个钱包，切换标签继续使用同一范围。全部／多选范围内，同币种钱包汇总，不同币种分别列出；历史归档钱包仍可选。流水的类型、分类、备注关键词筛选只影响流水列表。转账行显示两侧钱包，所选钱包命中任一侧时展示一次，且转账不计入收支统计。流水行、详情和删除确认明确显示所属钱包及币种。
- 点击流水行进入账目详情，详情底部提供“删除这笔账目”；确认弹窗展示日期时间、分类、类型及金额，确认后删除并刷新流水、收支统计和钱包余额，取消不改变记录。转账整体删除，原支出存在关联退款时需先删除退款，沿用前述约束。
- 统计展示所选期间的收入、可为负数的净支出和分类排行。空期间显示零金额及无账目提示。钱包余额始终按全部流水计算，归档钱包的历史流水仍参与相应期间统计。
- 所有统计按币种分别展示，不把不同货币直接相加，也不展示没有汇率依据的统一总资产。
- 转账不计收支；退款抵减支出；初始余额不计收入。余额公式包含所有流入流出，不能只用当月流水推算。

## 6. 外观、调色板与系统主题

### 6.1 独立的两个设置维度

入口：“设置 → 外观与调色板”。

| 设置 | 选项 | 默认 |
| --- | --- | --- |
| 明暗模式 | 跟随系统／浅色／深色 | 跟随系统 |
| 配色来源 | 预设调色板／自选主色／跟随系统壁纸（系统动态取色） | 预设调色板 |

明暗与配色来源可以自由组合，例如“茶绿＋跟随系统明暗”或“系统动态取色＋固定深色”。

### 6.2 预设与自选颜色

| 预设 | 种子色 |
| --- | --- |
| 杏橙（默认） | `#C47A4A` |
| 茶绿 | `#5F7F64` |
| 雾蓝 | `#587C9B` |
| 薰衣草 | `#8A729F` |
| 豆沙粉 | `#A76F82` |

- 自选主色同时支持可视化取色器和六位 HEX 输入，接受带或不带 `#`，保存为规范化不透明 RGB 颜色，不提供透明度。
- 第一次自选以杏橙初始化。无效 HEX 不允许应用，不丢失上次有效颜色。
- 预设与自选主色都通过 Material Color Utilities 的 Tonal Spot 色彩方案生成完整浅色与深色 ColorScheme，不把原色直接作为全部背景或正文颜色。
- 为主色、辅助色、卡片、背景、文字、边框、选中态提供统一主题颜色；业务页面不得散落硬编码品牌色。
- 收入、支出、成功、错误采用独立语义色，并适配明暗模式；配色不能让金额类型只能靠颜色判断。

### 6.3 系统跟随与兼容

- 明暗“跟随系统”响应系统明暗变化；固定浅色／深色时不跟随变化。
- 系统动态取色使用系统提供的 Material 配色，不自行读取或上传用户壁纸。
- 设置中的可见名称为“跟随系统壁纸”，对应现有 colorSource=SYSTEM，不增加另一套重复主题类型；与“跟随系统明暗”分别设置。UI 预览提供标明示意的动态色板，真实壁纸取色在 Android 中接入，不能将网页示意颜色当作实际读取结果。
- 动态取色在 Android 12／API 31 及以上可选；较早版本禁用该选项并说明版本要求。
- 恢复备份到不支持动态取色的设备时保留用户偏好，实际使用保存的预设，缺省为杏橙；明暗设置仍有效。
- 切换来源时保留上一次预设、自选主色，以便切回。
- 系统栏与应用内容统一适配；应用回到前台时也能刷新系统配色。

### 6.4 预览、保存和备份

- 调色页展示用餐卡片、收入／支出行、标签、按钮和背景预览。独立的“预览明暗”控件只切换示例区域的浅色或深色；“明暗模式”控件编辑将应用到全局的明暗偏好。
- 全局明暗、配色来源、取色器、HEX 和预设均先写入草稿，点击“应用”后全应用更新，无需重启。独立预览明暗与草稿一起使用，提交内容只包括实际应用偏好。
- 草稿与已应用的外观设置不同时，才显示示例、预览明暗及“取消”“应用外观”按钮。成功应用、取消或手动将草稿改回已应用值后，立即收起整个预览区。HEX 按规范化后的颜色值比较。
- 取消不改变已应用设置；“恢复默认”恢复跟随系统明暗、杏橙预设，仍通过应用按钮提交。
- 只在应用实际不同的设置时持久化并触发一次备份；拖动、无变化提交、系统明暗或壁纸变化不产生备份。
- 主题设置纳入 JSON 完整备份，换机后可以恢复。
- 普通正文及重要文字与背景的对比度验收目标至少为 4.5:1；极浅、极深和高饱和种子色都应保持可读性。 外观草稿预览使用与应用相同的颜色生成与组件样式，独立覆盖全部主题角色（含卡片底色、描边和主操作色），不继承已应用主题的对应派生色；为选中态、普通正文、辅助文字、主操作和危险操作分别校验前景／背景对比度，不限制自选种子色。

## 8. 技术架构与核心数据接口

### 8.1 结构

- 用 Kotlin 与 Compose 构建原生界面，统一使用 Material 3 设计系统。
- UI → ViewModel → Repository → Room；界面观察本地状态，备份服务不能成为读取业务数据的前置依赖。
- 按 `feature/meals`、`feature/ledger`、`feature/settings` 分包，核心能力放入数据库、主题／组件、备份、文件访问等共享包。
- 第一版采用按功能分包的单体应用，不为两个业务模块引入动态插件或独立后端。
- 新功能接入应用导航、首页卡片、自己的实体与业务逻辑，以及统一备份的导出／校验／恢复处理。
- 选择实施时相互兼容的稳定工具链和依赖，集中锁定版本；不得使用浮动依赖版本。实际 JDK、SDK 和构建命令验证后记录在 README 与 AGENTS.md。

### 8.2 实体与约束

| 对象 | 最低必需信息 |
| --- | --- |
| MealRecord | UUID、date、mealSlot、plannedAtHome（不可空布尔值）、mealMethodId（可空引用）、dishes、note、createdAt、updatedAt；日期与餐次唯一 |
| MealMethod | UUID、name、normalizedName、sortOrder、archived、showPreparationCategories；初始下厨／外卖 |
| Category | UUID、scope（PREPARATION／INCOME／EXPENSE）、name、normalizedName、sortOrder、archived、isDefault；同域规范化名称唯一，收支各有一个兜底项 |
| MealPreparationCategory | mealId、categoryId，唯一联合关联，多对多 |
| Wallet | UUID、name、normalizedName、currencyCode、currencyScale、openingBalanceMinor、sortOrder、archived、时间戳 |
| FinancialEntry | UUID、date、time（HH:mm，必填）、type（INCOME／EXPENSE／TRANSFER／REFUND）、walletId、amountMinor、categoryId、toWalletId、toAmountMinor、originalExpenseId、note、时间戳 |
| ThemePreferences | themeMode（SYSTEM／LIGHT／DARK）、colorSource（PRESET／CUSTOM／SYSTEM）、presetId、customSeedColor |
| ImportReceipt | kind（MEALS／LEDGER）、源文件 sha256、importedAt；随 JSON 迁移，防止同一无 ID CSV 重复导入 |
| DataState／备份执行状态 | 数据集标识、本地修订号、任务代次，以及各目标已确认的备份、待处理状态与失败信息；执行状态仅保存在本机 |

- FinancialEntry 的 walletId 对收入／支出／退款表示对应钱包，对转账表示转出钱包；toWalletId 和 toAmountMinor 只用于转账。
- 转账使用两侧钱包的货币精度；退款通过 originalExpenseId 引用原支出，分类从原支出取得。
- UUID 是业务数据身份，显示名称可改，所有关联用 ID，不用中文字符串作为外键或条件。
- 数据库中的金额为 Long；JSON 中金额与 revision 以十进制字符串传输，避免中间工具损失整数精度。具体字段与示例以 DATA_FORMAT.md 为准。
- 规范化分类名至少包含去除首尾空格和大小写无关比较；保留用户显示写法。各分类域不互相混用。
- 日历日期保存为 `YYYY-MM-DD`，不把当地日期先转换成 UTC 再按 UTC 分组；createdAt／updatedAt 使用 UTC。财务流水额外保存本地业务 time（HH:mm），与 date 配对；这不是创建时间，不随设备时区变化自动换算。日／月统计仍按记录的 date 分组，转账两侧共用同一业务日期和时间。
- 只在表单草稿允许 plannedAtHome 尚未选择。持久化、CSV 导入、JSON 恢复都必须满足其非空约束。
- plannedAtHome 为 true 时 mealMethodId 不可空；false 时可以为空。mealMethodId 为空时制作分类必须为空。
- 方式当前关闭分类开关不意味着历史分类非法，不能在数据库迁移或恢复时据此清空历史关联。
- 数据库 schema 与备份 formatVersion 分别版本化；升级必须显式迁移，不能用破坏性重建丢弃用户数据。

### 8.3 事务与统一变更入口

- 记录保存、关联分类创建、转账、退款、批量导入都走业务事务；成功后才向 UI 返回保存成功。
- 在业务事务内按 [DATA_FORMAT 的完整 JSON 保存约束](DATA_FORMAT.md#45-完整-json-的保存约束)校验提交后的数据。录入、编辑、批量导入及恢复写库共用规则。新增或加重结构超限时提示具体字段或总量并回滚，不增加修订或安排备份。已有超限数据按该节的整理规则处理，GitHub 容量按第 9.2 节处理。
- 所有可备份数据变更经统一入口增加修订号，并为已启用的备份目标登记最新待备份状态。
- 创建分类并保存记录算一次业务提交；CSV 批量导入算一次提交；主题应用一次算一次提交。
- 备份任务、进度、重试、系统主题变化等内部状态不能触发递归备份。
- 删除普通记录也增加修订号，后续完整备份反映删除后的数据。单设备完整快照方案不要求为将来的多端合并提前引入 tombstone 系统。

## 9. 完整 JSON 备份、本地自动备份与 GitHub

### 9.1 备份格式与边界

完整备份是可阅读的 UTF-8 JSON，不是直接复制运行中的 SQLite 文件。信封至少包含：

- 固定格式标识、formatVersion，及 backupKind（AUTO／MANUAL／PRE_RESTORE）。
- datasetId、snapshotId、revision、exportedAt。
- 按模块组织的用餐、用餐方式、制作分类、收支分类、钱包、流水、可迁移设置与成功 CSV 导入凭据。
- 稳定 ID、归档状态、排序、方式分类开关和主题偏好都必须保存，以支持真正完整恢复。

不包含 GitHub Token、Keystore 密钥、文件夹授权 URI、安装设备身份、工作队列、重试状态和远端同步游标。备份目标及其授权作为本机连接配置，不随业务 JSON 覆盖；换机后重新配置目录和 GitHub 连接。

- 稳定排序输出实体与字段，便于校验备份内容。
- 编写格式迁移器，支持已经发布的旧版本；无法识别的较新版本必须拒绝恢复，不可忽略未知模块后静默丢数据。
- 不导出密码，日志中不打印 Token。Android 系统备份及设备迁移按第 9.7 节处理。

### 9.2 最新完整数据的可靠性

- 自动备份的目标是让每个已启用目标最终都有一份覆盖最新已提交数据的完整 JSON。连续保存 A、B、C 时，待备份状态可以合并到 C。C 包含当时全部业务数据和可迁移设置，包括已生效的修改与删除。
- 业务数据与修订号在同一事务中提交。该事务同时持久化最新待备份状态，或通过数据库修订号与各目标已确认的修订号推导待处理状态。应用启动或后台任务恢复时据此补调度。保存成功以数据库提交为准，目录或网络故障期间仍可继续录入。
- 提交时核对完整 JSON 的累计数组元素数，达到结构上限的 80% 时提示接近容量。启用 GitHub 时，按导出规则估算完整 JSON 的原始字节数，达到 32 MiB 的 80% 时提示云端备份文件接近上限。两个预警均在设置中显示，批量导入预览显示本次提交的预计影响。
- 32 MiB 仅限制 GitHub 上传及恢复。结构合法的数据可继续本机保存及使用本地文件备份。实测快照超出云端上限时，将该修订的 GitHub 状态记为失败并提示使用本地文件，保留上一份成功的云端备份及其时间。当前修订只有在对应目标确认发布后才显示备份成功。
- 每个目标最多保留一个待处理的最新状态。任务执行时从数据库的一致性读事务生成完整 JSON，内容与备份标注的修订号一致。一个目标同一时间只执行一份，重试时读取当前最新数据，无需逐次生成或持久化中间修订的完整内容。
- 目标未配置时只保存数据与修订号，状态显示未配置。首次配置后登记当前完整数据待备份，GitHub 须先按第 9.4 节核对目标。
- 本地目录和 GitHub 分别跟踪完成状态。备份执行期间如果有新保存，完成时只确认此次实际写入的修订，最新状态仍待处理。若 C 在 A 执行期间提交，A 成功后按对应目标的调度规则备份 C。

### 9.3 本地目录

- 通过 Storage Access Framework 的系统目录选择器授权目录并持久化授权，示例位置为 `Documents/KitsuneBackup`；不申请全盘文件访问权限。
- 自动备份文件名使用 UTC 日期时间和同秒递增序号，例如 `kitsune-auto-20261118T093015Z-0001.json`。分配序号前核对目标目录中同一时间已有的名称，创建时遇到占用则取下一序号；换机复用目录也按同一规则。JSON 内保留独立的 snapshotId。
- 写入新文件，关闭流后读回并校验，再发布为有效备份。支持原子重命名的提供方可用重命名发布，其余可用独立的完成标记关联文件名、快照标识和内容摘要。恢复时只采纳已发布且通过校验的自动备份。
- 新文件发布前保留上一份有效备份。成功发布后只保留本次备份，清理范围限定为该目录中已确认由应用生成的同数据集 AUTO 文件及其标记。手动导出、恢复前备份和其他文件可独立保留。
- 记录已确认发布的快照标识后再清理旧文件。发布后清理失败或进程退出时，后续核对保留文件完整有效后补清理。恢复时可按文件名的日期时间及序号排列候选，遇到多份有效文件且无法确认发布先后时显示摘要供用户确认。文件名用于区分文件和浏览候选，设备时钟或本机修订号不决定清理对象。
- 目录失效、授权撤销、文件被移动、空间不足等情况显示错误与重新授权／重试入口，恢复访问后备份当前完整数据。
- 提供“立即备份”和“从文件夹备份恢复”。用户也可以通过系统选择器打开单独保存的 JSON 文件。

### 9.4 GitHub 私有库

- 用户提供目标私有仓库、分支和细粒度 Token，授权限定为该仓库的 Contents 读写权限；连接测试检查仓库和分支是否可用、是否为私有仓库。
- 数据仓库独立配置，不默认把个人生活数据提交到应用源码仓库。
- 通过 Contents API 更新固定文件 `backups/latest.json`。GitHub 会记录文件更新的提交，应用内的云端恢复读取该路径的当前文件。
- Token 使用 Android Keystore 保护的密钥加密后保存在本机，不写入源码、导出文件或日志。

#### 备份文件读取与大小限制

- GitHub Contents API 的读取上限为 100 MiB。首版云端备份上传及恢复采用 32 MiB 的应用上限，按未编码的 JSON 原始字节计算。下载检查元数据并在读流时累计字节数，上传在生成暂存快照时累计字节数。超过上限时停止相应操作，提示改用本地文件，保留待备份修订和已成功发布的云端备份。上传遇到超限时，等数据变化或用户手动重试后再检查。
- 先读取配置分支当前的提交 SHA，再以该提交 SHA 作为 `ref` 获取 `backups/latest.json` 的大小和文件 blob SHA。不超过 1 MiB 的文件可解码 Contents 对象中的 `base64` 并写入暂存文件。超过 1 MiB 且在应用上限内时，用 `raw` 媒体类型分块写入应用私有临时文件。两次读取使用同一个提交 `ref`，文件大小和 Git blob SHA 校验通过后才解析快照和生成摘要。
- 上传从 Room 的同一修订分批写出完整 JSON 到应用私有临时文件，在发起网络请求前结束数据库读事务。读取该文件，分块 Base64 编码写入 Contents API 的 `content` 字段。下载和上传的每个数据流读写缓冲均不超过 64 KiB，避免在堆中同时保留整份 JSON、Base64 和构造完成的 HTTP 请求体。恢复确认及覆盖仍以配置分支上该文件的当前 blob SHA 为准。
- 首版应用内的云端恢复只读取最新备份。需要较早版本时，可从 GitHub 对应提交下载原始 JSON，再走第 9.6 节的本地文件恢复流程。

#### 自动上传频率

- 首版在每批第一笔待上传变更提交后等待 1 分钟，窗口内后续变更只更新待上传修订，窗口不重新计时。仅在有待上传数据时安排 WorkManager 单次任务，同一目标串行上传。首次连接确认目标无备份文件时，首份备份免等合并窗口。
- 同一本机同一仓库、分支和路径的后台写入尝试，距该目标上一次写入请求发出至少 30 分钟。手动写入也计入上一次写入时间。自动上传同时满足合并窗口、写入间隔、失败退避和网络条件后才执行。频率参数在首版使用固定默认值，设置页可选择任意网络或仅 Wi-Fi。
- 断网时继续本地保存，联网且满足上述条件后只上传最新完整快照。重启后从持久化状态补调度。无待上传变更时不定时提交，后台任务的实际执行时间由 Android 调度决定。
- “立即备份”和用户明确确认的覆盖操作可跳过合并窗口及 30 分钟间隔，仍须遵守联网限制、失败退避、串行规则和远端校验。手动检查发现本机修订已成功备份且远端仍是对应版本时，显示“已是最新”。

#### 仓库容量提醒

- 在「设置 → GitHub 备份」提供「仓库容量提醒阈值」。默认 **800 MB**，接受可换算为 KB 的正整数 MB，输入无效时保留原设置。按 `1 MB = 1000 KB` 换算，直接比较原始 KB 值，容量严格大于阈值时进入超限状态。容量以 MB 显示并保留判断阈值所需的小数。该阈值只用于提示仓库整体容量，备份仍按单份快照的 32 MiB 规则执行。
- 每次 GitHub 自动写入确认成功后，先保存该次备份结果，再尝试通过 `GET /repos/{owner}/{repo}` 读取当前目标的 `size`（KB）。这是 GitHub 报告的仓库大小估计，可能滞后于刚完成的提交。查询复用已配置 Token，遵守现有联网、限流和 Worker 剩余时间。查询失败或跳过时保留最近一次成功读数和检查时间，下次自动备份成功后再查。查询结果不改变已确认的备份状态。
- 首次发现仓库超限时登记待提醒。App 在前台可展示时弹窗，后台发现时留到下次进入前台。弹窗显示仓库、最近容量和阈值，提供「稍后处理」和「查看 GitHub 仓库」。任一操作完成后记住本次已提示容量。同一轮超限期间，容量较上次已提示值再增加至少当前阈值的 10% 才再次提醒。容量回落到阈值或以下时清除本轮提醒记录，之后再次超限时重新提示。
- 保存新阈值时使用当前仓库的最近一次有效读数立即重判，无读数时等待首次成功查询。已有待提醒且仍超限时合并为同一提醒，已提示且仍超限时继续按增长规则去重。切换仓库时校验仓库 ID，新仓库不继承旧容量、待提醒或已提示值。旧目标请求迟到时忽略其结果。

#### 任务接续、计时与联网

- 同一目标允许一个正在执行的 Worker 和一个待执行请求。Worker 正常结束时重新读取持久化的最新待备份修订。若仍有可调度的工作，按当前条件安排后继请求。业务事务提交后也走同一调度入口，覆盖新修订在 Worker 最后一次检查之后才提交的情况。应用启动时补安排仍待处理但未入队的工作。
- 以目标和任务代次去重。已有 Worker 在运行时，后继请求要有独立的唯一工作标识，不可对运行中的同名任务使用 `KEEP` 后视作已经入队。`KEEP` 用于已有的等价待执行请求，`REPLACE` 仅用于替换尚未启动且调度条件已变化的请求。各代次共用同一目标的串行执行约束。Worker 取得该目标的执行权后重新检查代次和调度条件，再读取最新待上传修订。
- 同次开机期间用 `elapsedRealtime()` 计算 1 分钟窗口、30 分钟间隔和失败退避。持久化计时起点、等待时长及系统开机标识，进程重启后继续原计时。系统时间前拨或回拨时按单调时间重新核对尚未执行的任务，启动和 Worker 唤醒时再检查执行资格。设备重启后若无法可靠判断经过时间，首次检查时对尚未确认到期的计时按保存的时长重新起算，并记录新的计时起点。UTC 时间用于显示和记录。
- 仅 Wi-Fi 按 Android 当前可用于该请求的 Wi-Fi 传输判定。计费 Wi-Fi 仍可用，非计费移动网络仍应等待。通过 VPN 时，只有能确认实际承载为 Wi-Fi 才可执行。备份和恢复请求发出前重新核对网络，并使用已核对的网络连接。网络变化时停止不再满足条件的传输，避免自动切到移动网络。已发出的写入结果不明时，回到可用网络后先按冲突规则核对。后台暂不满足条件时保留待处理状态，网络条件满足后续调度。

#### Worker 超时与停止

- 普通 GitHub Worker 从本次 `doWork` 开始按单调时钟计 8 分钟的处理预算，涵盖生成或下载、解析、远端核对与传输，为 WorkManager 的普通执行时限留出清理余量。HTTP 连接、读写和整个请求都设置有限超时，且受剩余预算限制。处理预算耗尽时主动停止当前操作。
- 应用超时、系统停止或用户取消时，将取消传递给正在执行的 HTTP、文件读写和解析，关闭流并释放资源。取消或中断本身不登记成功。未确认发布的修订保持待处理，未完成的恢复保留原数据。临时文件和暂存库在操作结束后清理，进程被杀时在下次启动或执行前回收无活动任务引用的残留。恢复和核对所需的持久化状态须在发请求前写入，不能依赖 `onStopped`、`finally` 或任务返回值补写。
- 在写入请求可能发出前，持久化未确认的尝试及其远端前置条件。如果明确尚未发送写入请求，后续按调度规则读取最新修订。已发送或结果无法确认时，下一次网络允许的尝试先核对远端。已确认同一快照时只登记该次实际修订，原写入条件仍成立时才可退避后重新生成最新完整快照并整份重试，其他变化进入冲突处理。核对本身被中断时沿用待核对状态。任务不续传半成品。
- 应用主动超时后按既有退避及调度规则补安排。系统中止或进程退出后，由持久化状态和第 9.4 节的任务接续规则恢复。仅当真机验证表明受支持的备份确实需要更长时间时，才提供用户主动发起、带通知且可取消的长时 Worker，沿用相同的取消、数据校验与远端核对规则。

#### API 错误与重试

| 结果 | 处理 |
| --- | --- |
| `401` | 暂停 GitHub 操作并提示重新配置 Token。验证通过后再核对远端版本和待处理任务。 |
| `429` 或有明确限流信号的 `403` | 等待 `Retry-After` 指定的时间，并在 `x-ratelimit-remaining` 为 0 时等待 `x-ratelimit-reset`，两者均适用时取较晚值。用响应 `Date` 将绝对重置时间换算为等待时长。没有可用的等待指示时至少等待 1 分钟。若持续限流，采用有次数上限的指数退避，并显示限制原因。手动操作同样遵守限流等待。 |
| 其余 `403` | 暂停失败操作，提示检查 Token 授权、仓库访问权限或分支写入规则。 |
| `404` | 分别核实私有仓库、分支、Contents 读取权限和文件路径。仅在确认目标可访问且路径确实不存在时，按文件缺失处理。其余情况提示检查配置或授权，保留最近已接受的远端版本。 |
| `409` | 重新读取远端文件状态，按远端冲突规则核对未确认的尝试并比较原写入条件。仅在原条件仍成立时退避重试。 |
| `422` | 根据错误响应识别原因。有明确限流信号时按限流处理，疑似其他设备已创建文件时核对当前远端状态。参数、文件大小等校验错误提示修正原因后再试。 |
| `5xx`、网络错误或超时 | 保留待处理修订，按超时与停止规则核对可能已发出的写入，再按退避规则继续。 |

#### 远端变化与冲突

- 在本机按数据集 ID、仓库 ID、分支和路径保存 `lastAcceptedRemoteSha`。基准区分未确认、已确认文件不存在和已确认的文件 blob SHA。成功上传，或用户确认并成功恢复云端快照后，记录该次的文件 SHA。读取或预览新 SHA 不更新基准。首次配置时，须独立确认仓库及分支可访问，才能把路径不存在记为已确认。访问失败时暂停写入。
- 每次写入前核对配置和当前远端文件。现有文件的更新请求传入该次允许替换的 blob SHA，创建请求只适用于已确认不存在的路径。写入遇到并发错误时重新读取并比较，只有原写入条件仍成立才可退避重试。分支上的其他文件发生变更不构成备份冲突。
- 首次发现已有文件、已有备份被删除、文件 SHA 变化或远端属于其他数据集时，自动上传暂停。更换仓库或分支须重新核对并由用户确认目标。分支失效时提示检查配置。时间戳和不同设备的修订号不参与覆盖判断。发生冲突时继续保存本机数据和最新待备份修订。
- 设置页显示本机与云端摘要（时间、各类记录数量及可用状态），提供“恢复云端”“保留本机并覆盖云端”和“取消”。云端文件缺失时用明确的重建操作取代覆盖入口，并禁用恢复。取消后上传保持暂停。恢复采用第 9.6 节的完整替换流程。
- 用户确认覆盖或重建时，授权仅适用于摘要对应的目标及远端 SHA 或缺失状态。真正写入前再次核对，确认后远端再变化则暂停并要求重新确认。成功后采用实际发布的 SHA 作为基准，后续继续自动上传。
- 写入请求发出前持久化尝试信息。对结果不明的写入先核对远端，只有目标、数据集、snapshotId 和原始内容摘要均吻合才认领该次成功。若远端仍符合原写入条件，可按原条件退避重试并读取最新待上传修订。重试沿用同一远端前置条件，并保留尚未核对的尝试信息，以便识别此前请求迟到的结果。其他变化进入冲突流程。旧任务代次的结果仅用于核对远端，不能更新当前代次的成功状态。
- 完整恢复后，已绑定的 GitHub 上传保持暂停。用户可查看当前本机和远端摘要，再单独确认“用本机数据更新云端”。这次写入也遵守上述版本校验，成功后恢复自动上传。

### 9.5 状态展示

区分并分别显示：

1. 本地记录已保存。
2. 文件夹备份未配置／待处理／执行中／成功／失败，以及最新成功时间。
3. GitHub 未配置／待联网／待处理（包括等待上传间隔）／执行中／成功／失败／远端冲突／恢复后等待确认／需重新配置并确认，以及最新成功时间。

GitHub 备份设置同时显示最近一次读取到的仓库容量和检查时间。查询失败时标注当前无法更新，已有读数仍按上次检查时间展示。容量超限提示与备份状态分别显示。

后台任务受系统调度、休眠和强制停止影响。若最新修订仍在等待或失败，当前状态显示待处理或失败，另行显示上次成功时间。数据库写入失败时单独显示保存失败。

### 9.6 完整恢复流程

1. 逐块将本地文件或 GitHub 当前备份读入应用私有临时文件。按 [DATA_FORMAT 的解析与暂存规则](DATA_FORMAT.md#44-完整-json-的解析与暂存)流式解析和迁移，将数据分批写入独立的磁盘暂存库。
2. 在暂存库校验格式、字段限制、唯一性、ID 引用、金额精度、用餐必填条件、转账和退款约束，允许合法的历史归档引用。校验成功后才生成可确认的摘要。超限、空间不足、取消或失败时丢弃暂存数据，原业务库保持可用。
3. 展示来源、时间、各类记录数量，并明确完整恢复将替换当前业务数据，不进行合并。
4. 暂停业务写入和新的备份发布，未发出请求的旧任务停止发布。已发出的请求先等待返回，超时或响应丢失时按第 9.4 节核对结果。若本地文件恢复时无法核对 GitHub，保留旧尝试待联网核对，云端写入继续暂停。恢复来源为 GitHub 时，暂停旧任务后重新核对摘要对应的 SHA，云端已变化则刷新摘要并重新确认。
5. 数据库为空或只有未修改的初始默认数据时可直接恢复；存在用户数据或已修改设置时，先生成并校验独立的恢复前 JSON。可保存到已授权目录，也可通过系统文件选择器单次选定文件，适用于未配置目录的设备。用户取消导出或备份失败时保留当前数据并停止恢复。
6. 在数据库事务内整体替换业务数据和可迁移设置；任何失败都回滚。首次安装的默认分类不能在恢复后重复播种。
7. 保留本机连接配置。在恢复事务中作废旧待备份状态，建立新的本地修订与任务代次，并登记 GitHub 待确认状态。事务成功后可更新已授权目录的自动备份。GitHub 发布须按第 9.4 节单独确认，后续本机保存也遵循该状态。旧任务的结果不得回写新代次的完成状态。

恢复取消或失败时解除本次恢复的临时暂停，已有的远端冲突及确认要求继续生效。在途请求仍按第 9.4 节核对。

### 9.7 Android 系统备份与设备迁移

- 首版由应用的完整 JSON 备份与恢复负责迁移。Android 工程初始化时在 manifest 设置 `android:allowBackup="false"`，同时关联 Android 11 及更早使用的 `android:fullBackupContent` 和 Android 12 及更新使用的 `android:dataExtractionRules`。旧版规则及新版 `cloud-backup`、`device-transfer` 分别排除应用私有数据，包括 Room、目录授权、GitHub Token 和连接配置、任务数据库、远端 SHA、在途上传状态与暂存文件。覆盖内部、设备保护和应用专用外部目录的适用域，密钥留在本机 Android Keystore。用户自行保存的 JSON 文件按其文件提供方管理。
- 在不参与系统备份的 `noBackupFilesDir` 保存随机安装标识。初始化新业务库时在同一数据库事务内写入归属标记，备份配置与任务也绑定同一安装标识。应用和 Worker 在启用活动业务库、调度任务或发出写入前验证归属。正常重启和应用更新且归属一致时，沿用原状态。
- 若发现旧数据但安装标识缺失、归属不一致，或同一数据集及任务代次的备份确认修订高于当前本机修订，作废旧的连接、目录授权、远端基准和任务代次，暂停自动备份。可验证归属的业务库继续可用。无法验证归属的 Room 文件原样保留。用户可明确选择建立独立的新库，或按第 9.6 节从本地或 GitHub 的备份恢复。迁移待确认状态须持久化，重启不能把这批旧状态重新认定为本机有效状态。正常的修订落后、待备份和未确认写入按第 9.4 节接续。
- 文件夹备份在用户重新授权目录后恢复。重新配置 GitHub 后先检查仓库、分支及远端快照，要求用户确认当前文件版本或确认在文件缺失时创建。此前手动“立即备份”和旧 Worker 均不能发出云端写入。选择恢复云端仍执行第 9.6 节的校验、摘要确认和本机保护，恢复后按原流程单独确认是否更新云端。

## 10. CSV 导入导出

CSV 用于表格查看、批量录入和记录迁移；完整钱包、分类设置、主题和全部关系迁移优先使用 JSON。

### 10.1 标准模板

- 提供 UTF-8 编码的用餐、记账模板和导出文件；导入接受 UTF-8 BOM，正确处理引号、逗号和多行字段，不能按字符串逗号简单切分。
- 使用固定英文列名，并在模板说明中提供中文解释、枚举值和示例。导出保留稳定记录 ID。
- 用餐表列：`id,date,meal_slot,planned_at_home,meal_method,preparation_categories,dishes,note`。
- 记账表列：`id,date,time,type,wallet,currency,amount,category,to_wallet,to_currency,to_amount,original_expense_id,note`。
- 日期格式为 `YYYY-MM-DD`；meal_slot 为 `BREAKFAST/LUNCH/DINNER`；planned_at_home 为 `true/false`，不能为空。
- meal_method 使用方式名称；preparation_categories 是分类名称的 JSON 字符串数组，嵌入 CSV 时遵守 CSV 引号转义规则，空数组表示无分类。
- 财务 type 为 `INCOME/EXPENSE/TRANSFER/REFUND`；金额为十进制文本，无千分位和货币符号，不能使用二进制浮点读写金额。
- 记账 time 必填，采用严格的 24 小时制 HH:mm，范围 00:00 至 23:59；不接受秒，不把缺失时间默认成午夜或创建时间。
- TRANSFER 填写两侧钱包、币种和金额；非转账对应列留空。REFUND 填写 original_expense_id，分类由原支出确定。
- 金额精度超过币种支持范围时报告错误，不在导入时默默四舍五入。

### 10.2 预览与提交

- 先完成解析、名称映射和全量校验，再展示新增、重复和错误记录及具体行号。
- 钱包映射到已有钱包并校验币种；缺少钱包时先创建再导入，不通过 CSV 隐式猜测初始余额。
- 未知用餐方式需在预览中映射到已有方式，或先到设置中创建；不能猜测其分类开关。
- 新制作分类、收入分类和支出分类按各自域随导入创建；分类同名匹配现有 ID。
- 相同 ID 且业务内容相同的记录跳过；相同 ID 内容不同，或不同 ID 占用同一日期餐次时，报告冲突，不覆盖现有数据。
- 无 ID 的外部记录生成 UUID；记录成功导入文件的摘要，阻止同一文件反复导入造成重复。具有不同 ID 的合法同金额账目不能仅凭金额或备注去重。
- 退款可以引用已有支出或同批导入的支出，整体校验所有引用和累计退款额；转账作为一个整体导入。
- 若任何行有错误，要求修正后再整批提交；重复项可跳过，有效新增项在同一事务中提交并触发一次备份。
- 新导入方式为空且计划在家吃为是的用餐记录必须报错；历史制作分类的保留规则与 JSON 恢复一致，不能因方式目前关闭开关而静默丢弃分类。

## 13. 验收与测试计划

### 13.1 用餐

- 新记录未选择在家吃不能保存；选是但未选方式不能保存；选否且方式为空可保存。
- 选否时仍可选择下厨／外卖或自定义方式；是改否保留内容。
- 下厨显示多选制作分类，外卖默认不显示；新增方式开关按设置生效，改名不影响引用。
- 新分类保存后可再次下拉选择，取消不创建；同日同餐冲突不能覆盖。
- 关闭全局开关后历史分类仍可查看，修改备注不丢失历史分类；主动切换到不支持分类的方式后按规则清除。
- 月度方式分布和分类计数正确，未填方式独立统计，中文与多行文本完整保留。

### 13.2 记账

- 验证四种流水的时间必填、默认当前分钟、补录和编辑保留、00:00／23:59 边界及非法时间拦截；同日排序正确，设备时区变化后业务日期时间不漂移，跨日与跨月统计按填写日期归属。
- JSON／CSV 往返保持时间，缺失或非法 time 报错；相同 ID 但业务时间不同视为冲突。

- 计算器验证运算优先级、除零、非法表达式、非正数及单笔金额超界。验证 `1÷3×100` 在两位小数钱包中得到 `33.33`，JPY 按整数舍入。
- 覆盖 JPY 整数精度、两位及其他支持币种精度；货币间不混合加总。
- 同币种转账、跨币种双金额、整体编辑删除正确影响两侧余额，不计收支。
- 多次部分退款、超额退款拦截、退款删除、原支出修改约束及跨月净支出统计正确。以 A 支出 100、B 同币种退款到账 30 验证钱包范围内的 100、−30、70 及原支出分类归属。
- 流水选择跨月日期范围后，流水、摘要和统计一致并显示同一起止日期。覆盖包含边界、非法日期范围、取消、返回按月和跨标签保留条件。
- 钱包初始余额、负余额、归档和已有流水后的币种限制正确。覆盖删除抵消支出后余额超过 64 位上限，仍可保存并精确显示结果。

### 13.3 外观与图标

- 三种明暗模式与三种配色来源组合正确；旧系统动态取色选项与恢复回退正确。
- 自选 HEX 校验、独立浅色／深色预览、应用、取消、恢复默认、重启与 JSON 恢复正确。切换预览或编辑明暗草稿不影响其他页面；取消后保留此前应用的明暗与配色。
- 打开设置时预览区隐藏。修改明暗、配色来源、预设或自选主色后显示；取消、成功应用或把草稿改回已应用值后隐藏。无效 HEX 阻止应用，预览区保持可见以便修正或取消。
- 首页同时展示 CNY、JPY 等已有币种的本月收支，金额分别标记币种，快捷记账按钮只有一个。
- 切换用餐和账本时，核对页标题、筛选、列表、表单和统计使用第 3.1 节的共用样式；检查两套视觉在浅色、深色及窄屏下的布局，验证长菜品、长备注、长钱包名和大额金额的展示。
- 拖动不备份，系统变色不备份，一次实际应用只生成一次修订。
- 检查所有页面、弹窗、表单、图表、计算器、系统栏、大字体和键盘布局；验证关键文字对比度。
- 狐狸图标在圆形／圆角方形遮罩及小尺寸下不裁掉耳朵或五官；彩色和单色主题图标都可辨认。

### 13.4 备份、导入与恢复

- 目录不可用或断网时连续提交 A、B、C，保存均成功且每个目标的待处理状态合并到 C。恢复访问后能从备份恢复 C 的完整数据，包含期间的新增、修改和删除。
- 在 A 执行期间保存 B、C，验证 A 的完成只确认 A，最终两个已启用目标都能备份 C。验证数据库提交后、后台任务调度前进程退出，重启可补调度。
- 覆盖写入、校验、发布和清理各阶段中断。只有发布成功的文件可用于自动恢复，新文件发布前上一份仍可恢复，清理成功后目录中只剩本数据集最新一份 AUTO。验证不支持原子重命名的目录及手动导出、恢复前备份和其他数据集文件的保护。
- 验证同秒生成文件、设备时钟回拨和换机后复用旧目录。命名碰撞时已有文件仍可恢复，新备份发布成功后保留该份。
- 覆盖断网、目录失效、授权撤销、外部空间不足、进程退出和重启补任务；状态不得误报成功。
- 验证编辑含中文、换行和转义字符的字段，达到结构上限可保存，超过上限则指出具体字段。并发提交、批量导入、编辑关联与删除后核对累计数。验证达到 80% 时出现对应提醒，只有云端超限时录入和本地备份可继续，GitHub 明确显示当前修订失败及上次成功时间，后续缩小快照可恢复上传。
- 验证首笔变更后 1 分钟合并、后续变更不推迟窗口、后台写入间隔至少 30 分钟、空闲无提交和断网恢复只上传最新修订。验证保存恰好发生在 Worker 退出时也会安排后继，进程重启可补调度，恢复或切换目标后的旧任务不能写入。验证“立即备份”只跳过普通频率限制。
- 验证系统时钟前拨、回拨、进程重启和设备重启时，合并窗口、间隔与退避符合计时规则。仅 Wi-Fi 模式覆盖计费 Wi-Fi、非计费移动网络、VPN 承载不明和写入中切网。
- 验证 1 MiB 下载方式切换及 32 MiB 应用上限，覆盖大文件 `raw` 下载、元数据与下载之间更新分支、字节数或 blob SHA 不符、流式 Base64 上传，以及从本地 JSON 恢复较早提交中的快照或超过云端应用上限的有效文件。低内存真机记录大文件导出和恢复的峰值堆占用，确认没有整份文件级内存分配。超限、结构校验失败及空间不足时保留本机与原有云端备份。
- 验证自动备份成功后才检查仓库容量。默认 800 MB 时，`size` 等于 800,000 KB 不提示，高于该值才提示。覆盖无效阈值不覆盖原设置、改值后立即重判、后台完成后下次打开 App 提示、关闭后重启去重、再增长达到阈值的 10% 及回落后的重新提示。查询失败、限流或目标切换不得误报容量或变更已成功的备份状态。
- 在生成、下载、解析、上传前与请求可能已发出时分别模拟应用超时、系统停止或进程终止。验证未完成工作不记成功、旧修订仍可核对、后继优先核对不明写入并在可重试时重新生成最新完整快照。覆盖远端已接收、仍是原版本和第三方修改，以及临时文件与暂存库的回收。
- 按 GitHub API 错误表逐项验证，重点检查权限错误不会被判定为文件缺失、限流未到期不能重试、`409` 和疑似并发创建的 `422` 不会覆盖远端较新版本。
- 两台设备依同一 SHA 并发上传，后写入者须暂停。覆盖首次绑定同时创建、首次已有文件、文件被删除、其他数据集替换、更换分支、Token 失效和确认后远端再次变化。验证取消保留待上传修订，重建需确认，分支的无关提交不阻塞备份。
- 覆盖上传响应丢失时远端已发布、仍是原基准和已被其他设备替换的情况。覆盖恢复期间旧任务尚未发出或已发出请求，以及本机离线恢复后补核对；旧结果不能解除暂停或确认新代次的修订。
- 在全新安装中恢复完整 JSON，用餐、方式配置、分类、钱包余额、退款／转账关系、归档状态和主题一致。
- 检查合并后的 manifest 和两版 XML，并覆盖旧版 Auto Backup、新版云备份及设备直传。模拟仅复制 Room、仅复制连接／任务状态、安装标识缺失或不符、同代次本机修订倒退，验证未归属旧库不会静默变为活动库，旧任务不能使用旧 Token 或发布。重启后仍须重新配置并确认当前目标，覆盖有文件和缺失文件两种情形。同一安装正常重启和版本更新可按原状态继续。
- 覆盖全新安装直接恢复、有数据但无授权目录的单次保护导出及导出取消或失败。已绑定 GitHub 时，恢复后继续录入、重启或手动发起备份均须保持远端文件，直到用户另行确认用本机数据更新云端。
- 损坏或较新格式、无效引用、无效金额、日期餐次冲突及失败恢复都不能破坏现有数据。
- CSV 覆盖中文、引号、逗号、多行文本、制作分类数组、重复 ID、重复文件、同批退款引用、精度错误和整批回滚。
- 凭证不出现在导出文件、仓库或日志中；备份任务变化不会递归触发新备份。
